# Project menu

Choose one project with Aden after you have completed the Northline observation and scoped your first reviewed change. Bring a person who has the problem and the baseline from the Reality Gate reading. Aden helps you choose a useful version that fits the intensive. You can propose your own problem after the intensive using the same review.

Every project needs one real user, permission to use its data, a baseline, a check that can fail, a cost model, a running version, and feedback from the person using it. An incident report may describe a deliberately injected failure when no real incident has occurred; label the exercise. Three-dimensional graphics are optional. A clear screen recording of a useful workflow is enough.

Start with one workflow, one type of user, and one external integration at most. Use the project templates for the specification, checks, AI work record, incident, measurement, and demo. A second project can wait until the first has a running version, a recorded demo, and a reviewed result.

## Workflow compression

Help a service coordinator turn a technician's notes into a draft job record. Begin with pasted text and a review screen. The coordinator checks the proposed fields before saving. Keep estimates, messages, and commitments under human approval.

Measure the time to produce a usable record, including corrections, on comparable examples before and after. Check missing fields, invented parts, and ambiguous quantities against a small labeled set. Report cost per accepted record and the fraction that needed correction. Your demo shows the original note, the proposed record, a rejected mistake, and the final saved result.

## Reconciliation

Help a club treasurer or small-business administrator compare exported orders with invoices and identify unmatched items. Begin with two approved, redacted files. Use code for amounts and matching rules. If AI explains an anomaly, make it point to the source rows.

Measure time to resolve a batch and the number of true mismatches found, missed, and falsely flagged. Include duplicate rows, rounding, time zones, and missing identifiers. Keep the tool read-only; moving money is outside the course project. Show one discrepancy from source to resolution and the cost per batch.

## Intake and follow-up

Help an organizer turn requests into a review queue with proposed next steps. Begin with one intake form and a draft reply. A person approves any external message or appointment. Keep a record of state changes so a retry cannot send a second reply.

Measure handling time and unresolved requests. Test repeated events, unavailable calendar data, attempts to inject instructions into a request, and a withdrawal of consent. Show a successful request, a stopped action, and the human handoff. Include tool and hosting costs.

## Reliability rescue

Help a maintainer diagnose one recurring failure in an existing service. Reproduce the failure in a safe copy, trace the cause, add a check that catches it, and repair the smallest responsible part.

Measure a relevant error rate or recovery time with the same workload before and after. Include a rollback, logs with secrets removed, and the case your check still misses. Show the failing behavior and repaired behavior side by side. Count monitoring and operating costs. An instructor-owned service is acceptable if you label that relationship and arrange an independent review later.

## Match replay theater

Help a player or session organizer investigate where a multiplayer session became confusing. Capture a consenting test session and build a replay with a timeline. Use three-dimensional graphics if they clarify movement; a two-dimensional view may be easier to build and inspect.

Compare time to locate a known event with and without replay. Test a dropped event and disagreement with the authoritative server record. State retention and storage cost per session. A cohort playtest is a cohort playtest; describe public usage only after you have observed it.

## Agent arena with visible cost

Help a developer compare assisted solutions to a bounded set of past tickets. Display the proposed change, independent checks, human acceptance, and cost. Start with one repository and a few tasks the developer knows well.

Measure accepted solutions per attempt and cost per accepted solution. Separate development examples from held-out evaluation tasks. Include a wrong solution that passes a weak check, then improve the check. Do not give an agent permission to change the check used to grade its own result. This project is distinct from the timed Arena assessment everyone takes.

## Choosing together

Pick the project whose user you can reach and whose result you can check. If two choices fit equally well, choose the one you would enjoy showing. Keep additional visualization and infrastructure ideas as later extensions. At project review, bring your Reality Gate answers and stack decision. Aden records acceptance before you build.

**Done when** you have chosen one project, identified its user, recorded its baseline, and received Aden's acceptance of the first version.
